# Threat Model

**Status: Discovery in progress.** This file defines the template and
method the actual system threat model will use. It contains three real,
evidenced findings below (from the `hr-legacy` deep-dive, `auth` and
`advances` modules); everything else remains pending further Discovery
passes. Do not fill in specific threats, mitigations, or residual risk
ratings based on assumption — every row must cite evidence.

**The `dashboard/pages/employees/page.php` row below is the single most
severe finding of the entire Discovery pass** — it is a direct
cross-tenant account-takeover path, not just data tampering. **The two
`auth`-module rows further down are the second most severe** — if `AppConfig::DEBUG` is `true`
in the live production deployment (already flagged as unconfirmed-but-real
in `docs/legacy/production-behavior-evidence.md`), both OTP-issuing
endpoints hand the real OTP code back in the API response, making every
account on the platform — any company, any employee — takeable over by
phone number alone, no WhatsApp access, no brute force, no guessing
required.

## Method

STRIDE (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of
Service, Elevation of Privilege), applied per trust boundary once the
boundaries below are actually known. This is an explicit choice, not a
placeholder — if a future architecture decision picks a different method,
record that as an ADR and update this line.

## Scope (to be completed during Discovery)

- **Assets**: what data and capabilities need protecting (employee/customer
  PII, attendance/biometric data, authentication credentials, tenant data
  isolation, source code, CI/CD credentials)
- **Actors**: who interacts with the system (employees, admins, customers,
  attendance devices, vendor APIs, internal agents/automation)
- **Trust boundaries**: where control or privilege changes (client <-> API,
  API <-> database, tenant <-> tenant, edge gateway <-> device, edge gateway
  <-> cloud, agent <-> repository)
- **Data flows**: how data moves across each trust boundary above

| Public/tenant ↔ session lifecycle, `apis/helpers/functions.php` + `apis/config/constants.php` | Spoofing, Elevation of Privilege | JWTs are valid for `AppConfig::JWT_EXPIRE_HOURS = 87600` hours (**10 years**) from issuance, for both auth types. For the `employee` auth type, a server-side `token_version` check gives *some* revocation — but only a **fresh login** bumps it (`employee_issue_session_token()`, called from `login_employee.php`/`login_desktop.php`'s HR path); neither `reset_password.php` nor any `profile/*` endpoint bumps it, so changing or resetting a password does **not** invalidate an already-issued employee token. For the `company` auth type (`login_company.php`, `login_desktop.php`'s admin path), there is no `token_version`-equivalent check at all — a company-admin JWT, once issued, cannot be revoked server-side by any means short of rotating the global `JWT_SECRET` (which would invalidate every tenant's sessions simultaneously). | Requires an already-leaked/stolen token (via any other vector — device compromise, log exposure, MITM, etc.), not a novel exploit path on its own — but the 10-year window means a token leaked once via *any* means remains a standing risk for years, and for company-admin tokens specifically there is no operational response available (short of the global-secret nuclear option) even after the leak is discovered. | High — a single leaked long-lived token, especially a company-admin one, grants durable, effectively unrevocable full-tenant access. | Employee tokens: partial (a fresh login by the legitimate user invalidates prior tokens, but nothing prompts that to happen after a suspected leak other than the user voluntarily logging in again). | Within-tenant, `role=hr` privilege scope | Elevation of Privilege | `employees.hr_permissions` is a real 18-boolean-flag matrix (`can_employees`, `can_company_settings`, `can_payroll`, etc. — see `docs/migration/database-schema-inventory.md`), clearly designed so a company admin can grant an HR employee narrow, feature-specific access. In practice, only ~21 of the roughly 150+ endpoints reachable by `role='hr'` actually call `require_hr_permission()`/`require_company_settings_access()` to check it: `administrative_decisions/*` (5), `attendance_exception_types/{create,delete,update}.php` (3), `company_official_holidays/*` (5), `company_settings/*` (6), `company/update.php`, `employees/update.php`. | **Tenant ↔ tenant, `dashboard/pages/employees/page.php` — CROSS-TENANT ACCOUNT TAKEOVER** | Spoofing, Tampering, Elevation of Privilege | `save_edit`, `deactivate`, `reactivate`, and `delete` all mutate the `employees` row identified by a raw POSTed `id` with **no check that the employee belongs to the session's own company** (confirmed: `hr_is_scoped_company()`/`getCurrentCompanyId()` are read into `$isComp`/`$compId` at the top of the file but never compared against the target employee's actual `company_id` before any of these four actions run). Critically, `save_edit` accepts an optional `password` field and, if present, sets `password_hash = password_hash($_POST['password'], PASSWORD_BCRYPT)` directly on the target row. A logged-in company-admin or HR user for **any** tenant can therefore submit another tenant's employee `id` with a new `password` value and directly overwrite that employee's login credential — then authenticate as them (dashboard HR/Manager login or the mobile API's employee login both check only `password_hash`) with full access to that employee's account and, depending on their role, everything that role can reach. `deactivate`/`reactivate`/`delete` carry the same missing check, so cross-tenant employee deactivation and deletion (with `dbDelete()`, not the API's careful cascade-delete helper — likely to throw an unhandled FK-constraint error rather than cleanly cascade, given `payslips.employee_id` has no `ON DELETE` clause per the schema inventory) are also reachable this way. | Requires only a valid dashboard login for any one tenant (company-admin or HR password) plus a guessed/observed numeric employee ID — no cross-tenant credential needed. | **Critical** — direct path to impersonating any employee at any company on the platform, not merely tampering with their data; strictly worse than every other finding in this register except the DEBUG-gated OTP disclosure (which is unconfirmed-live), because this one requires no precondition beyond a single ordinary tenant login. | None found in code. | **Open — unmitigated, present in the live production system.** | Unassigned — recommend treating as the top remediation priority alongside confirming the `DEBUG` value, ahead of the other IDOR findings in this register. | `workin-hr/hr-legacy` commit `83c326e40f68dd0d560595a6c4e465eb681f2ce8`: `dashboard/pages/employees/page.php` lines 1–6 (`$isComp`/`$compId` read but unused for authorization) and lines 112–184 (`save_edit`/`deactivate`/`reactivate`/`delete`, no company check on any of the four). |
| Tenant ↔ tenant, `dashboard/pages/{advances,penalties,payroll,requests,leave_balances,assets,administrative_decisions,complaints,notifications,company_settings}/page.php` | Tampering, Elevation of Privilege, Information Disclosure | The dashboard is a separate codebase from `apis/` with its own action-handling pattern, and it independently reproduces the same class of cross-tenant gap already found in the API's `advances` module — but here it spans at least 10 modules, confirmed by direct reading, not sampling: `advances/page.php`'s `approve`/`reject`/`mark_paid`/`delete_advance`; `penalties/page.php`'s `mark_applied`/`delete_penalty`; `payroll/page.php`'s `finalize`/`reopen`/`delete_run`/`edit_detail` (directly rewrites a payslip's `basic_salary`/`allowances`/`net_salary`); `requests/page.php`'s `approve`/`reject`/`delete`; `leave_balances/page.php`'s `edit_leave`/`delete_leave`; `assets/page.php`'s `edit_asset`/`mark_returned`/`delete_asset`; `administrative_decisions/page.php`'s `edit_decision`/`delete_decision`; `complaints/page.php`'s `reply`/`set_status`/`delete`; `notifications/page.php`'s `delete`; `company_settings/page.php`'s `request_types`/`exception_types` sub-actions. In every case, the action fetches or mutates the target row by a raw POSTed `id` with **no check that it belongs to the session's own company** — `includes/query.php`'s generic `dbUpdate()`/`dbDelete()`/`dbFind()` helpers have no built-in tenant scoping at all (confirmed by reading the file); each page is individually responsible for adding it, and these don't. **A working, reusable fix pattern already exists elsewhere in this same codebase and is not a hypothetical remedy**: `includes/org_helper.php`'s `org_verify_post_row($table, $id, $companyId)` is called once, before the action switch, in `branches/page.php`, `departments/page.php`, `job_titles/page.php`, and `shifts/page.php` — all four correctly reject a cross-company `id` before any mutation runs. Every module's "add/create" action (`add_advance`, `add_penalty`, `add_leave`, `create_run`, etc.) across the *affected* modules also independently re-derives the equivalent check inline — proving the pattern is well understood throughout this codebase and specifically omitted only on the decision/mutation-of-existing-row actions. | Requires a valid dashboard login (company-admin or HR password) for *any* one tenant — no cross-tenant credential needed — plus a guessed or observed numeric ID for the target row. Session-based, CSRF-protected form submission, but CSRF protects against a third party forging the request on the *victim's* behalf, not against the legitimate (if malicious) logged-in user submitting a modified `id` themselves. | High — direct financial/operational data tampering (approve/reject/pay/delete advances and penalties, finalize/reopen/delete payroll batches, directly edit payslip amounts, approve/reject/delete leave requests, tamper with company assets/decisions/complaints/notifications/settings) across at least 10 confirmed modules. Only these were read directly in this pass; the remaining dashboard action-handling pages following the same pattern were not all individually verified and should be treated as suspect until checked. | `org_verify_post_row()` exists and correctly protects 4 modules (`branches`, `departments`, `job_titles`, `shifts`) — it is a ready, minimal fix to extend to the affected modules, not something that needs to be designed from scratch. | **Open — unmitigated for the 10 confirmed modules, present in the live production system, independent of the API-layer finding above (separate codebase, separate bug).** | Unassigned — recommend extending `org_verify_post_row()` (or an equivalent) to every affected module as a single coordinated fix, alongside the `employees/page.php` finding below. | `workin-hr/hr-legacy` commit `83c326e40f68dd0d560595a6c4e465eb681f2ce8`: file/line references per module listed above; `dashboard/includes/query.php` (no tenant scoping in generic helpers); `dashboard/includes/org_helper.php` (`org_verify_post_row()`, the existing correct pattern). |

| Platform-wide, `dashboard/includes/auth.php` `doAdminLogin()` | Spoofing, Elevation of Privilege, Repudiation | The dashboard's "platform admin" role (`$_SESSION['admin_logged_in']`) is gated by a single shared password (`ADMIN_PASSWORD`, or an optional `ADMIN_PASSWORD_HASH`) — not a per-person account. There is no username, no individual admin identity anywhere in this login path, and `isAdmin()`/`getCurrentCompanyId()` place no company restriction on the resulting session: this is unscoped access to every tenant on the platform. Because there is no identity behind the session beyond "knows the password," any action taken as admin is **not attributable to an individual** (no audit trail differentiates one admin-password holder from another). This is architecturally distinct from (and arguably a design choice, not a bug like the findings above) the two IDOR findings — it is a single, deliberately powerful account, but one with none of the accountability controls that level of access usually warrants. | Requires knowing the one shared password. Real mitigations exist around it: `security.php` enforces an 8-attempt lockout (15 minutes) and the password can be bcrypt-hashed rather than compared in plaintext — this endpoint is meaningfully better-defended than the OTP-disclosure finding above. | Medium-High if the password is ever shared broadly, written down insecurely, or leaked (e.g. it was among the real values found in `dashboard/includes/constants.php` during this repository's sanitized import) — full cross-tenant access with zero per-actor accountability. | Login-lockout and optional password hashing (see Likelihood). No per-admin identity, no MFA, no rotation mechanism observed. | **Open — accepted-by-design risk, not a code defect; worth an explicit decision on whether individual admin accounts and MFA are warranted before or during migration.** | Unassigned. | `workin-hr/hr-legacy` commit `83c326e40f68dd0d560595a6c4e465eb681f2ce8`: `dashboard/includes/auth.php` (`doAdminLogin()`, `isAdmin()`), `dashboard/includes/security.php` (`admin_password_valid()`, lockout functions), `dashboard/includes/constants.example.php` line 26–27. |
