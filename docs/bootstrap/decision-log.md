# Decision Log

Each decision is tracked with: Decision ID, Date, Decision, Status, Owner,
Related ADR, Reason, Impact, Follow-up, Evidence. Status is always one of
`Proposed`, `Accepted`, `Rejected`, `Superseded`, `Deferred` — matching the
vocabulary used for ADRs. A decision that restates an ADR's direction
carries the same status as that ADR; it is not allowed to claim more
certainty than the ADR it depends on.

## D-085: The Self-Generated Employee Spreadsheet Must Round-Trip — Two Reader Defects Corrected, Generators Untouched

| Field | Value |
|---|---|
| Decision | Phase 1 keeps `employees/template_excel.php`'s output byte-for-byte as legacy produces it -- the CSV's UTF-8 BOM, the salary group row, the 28 Arabic headers, and the XLSX's group row, merges, styles and layout -- and **corrects the reader** so that a template the application itself generated can be read back by `analyze_excel` and `import_bulk`. Two defects in `employee_excel_load_rows()` are in scope and nothing else: (1) the CSV branch's inverted BOM handling, which must consume the BOM exactly once and then recognise the salary group row; (2) the XLSX branch's fallback condition, which must not treat "the workbook contained no data rows" as "the workbook could not be read". Java never re-parses ZIP bytes as CSV. |
| Status | Accepted 2026-08-21 (owner's Option 2). Root-caused; implementation is the JDK-only reader/writer port. |
| Owner | Repository owner, explicit direction in this conversation, 2026-08-21, after the generated-template round-trip probe. |
| Related ADR | `docs/adr/ADR-0011-phase-sequencing.md` (strict parity, and the rule that any divergence carries its own decision); D-058 (evidence precedence, no silent defect fixes); D-079. |
| Reason | The two endpoints form one product flow, and measured against the real PHP the flow does not work: a blank template downloaded from `template_excel.php` and uploaded straight back is rejected by `analyze_excel.php` in both formats. Reproducing that faithfully (Option 1) would ship a bulk-import feature that cannot accept its own template; fixing the generators as well (Option 3) would change bytes clients already hold. Correcting the reader alone is the smallest change that makes the round trip work, and it leaves every generated file unchanged. |
| Measured root cause | **XLSX -- the writer and the parser are both correct.** The generated workbook is a valid ZIP with the expected six entries; `xl/_rels/workbook.xml.rels` resolves `rId1` to `xl/worksheets/sheet1.xml`, which is present; `XlsxParser::parse(false)` reads it and returns exactly two rows, the group row (recognised by `employee_excel_is_salary_group_row()`) and the 28 headers. The failure is in `employee_excel_load_rows()`'s condition `($format === 'xlsx' && $rawRows === [])`: after shifting the group and header rows off a blank template, zero data rows remain, the condition fires, and the function re-opens the `.xlsx` as CSV -- yielding **15 rows whose keys are raw deflate bytes**, which `analyze()` reports as 15 invalid employees. With a single data row present the same path works perfectly (`total=1, valid=1`, ids resolved), which is what confines the defect to files with no data rows. **CSV -- the BOM logic is inverted.** `$bom = fread($handle, 3); if ($bom !== BOM) { rewind(); } ... if ($bom !== BOM) { fread($handle, 3); }` skips three bytes when there was *no* BOM and keeps the BOM when there was one. On the generated file the BOM stays glued to the group row's first cell, `employee_excel_is_salary_group_row()` no longer matches, the group row becomes the header row and the header row becomes data: a blank template analyses as one invalid employee, and a template with one valid row analyses as **two** invalid employees. `employee_excel_read_headers()` has its own, correct BOM handling, which is why `assert_template_structure()` passes while row loading is corrupted. |
| Impact | Java's reader consumes the BOM exactly once, recognises the salary group row on both paths, and treats an empty result as an empty result. Expected after the correction, and to be proven by test: a generated blank CSV and a generated blank XLSX both analyse to `total=0`; each plus one valid row analyses to `valid=1`. Generators are byte-unchanged. `employee_excel_read_headers()` and `employee_excel_assert_template_structure()` need no correction and get none. |
| Explicitly out of scope | The English `label_en` collision -- "Mobile attendance (required)" normalises to `phone`, because `phone` carries the alias `mobile` and the alias rule accepts `mobile_attendance…` via its `alias_` prefix match. It is real, but the template emits `label_ar`, whose 28 headers normalise to exactly the 28 canonical keys with no duplicate, missing or unknown column. Not fixed under this decision. |
| Follow-up | The same two reader defects exist in `hr-legacy` and are not fixed there by this decision; if the PHP application stays in service alongside Phase 1, its own bulk import remains unable to read its own blank template. Worth an `hr-legacy` issue, tracked separately from this repository. **J2 stays unresolved**: the duplicate case-folded lookup-name question is untouched here, and no `ORDER BY` is invented for the name lookups. |
| Evidence | Probes run against a real PHP 8.3 CLI with the `zip` extension, the vendored schema in MariaDB 11.8, and the endpoint's own code path (`employee_excel_template_headers()`, `employee_excel_template_group_row()`, `stream_employee_template_xlsx()`, `stream_styled_xlsx()`) -- no hand-built fixtures: the ZIP entry listing and rels resolution; `XlsxParser::parse(false)` returning 2 rows for the blank workbook; `employee_excel_load_rows()` returning 15 ZIP-byte rows for the same file; `employee_excel_analyze()` reporting `{total:15, valid:0, invalid:15}` for a blank XLSX and `{total:1, valid:0, invalid:1}` for a blank CSV; and the with-data-row runs, `{total:1, valid:1}` for XLSX against `{total:2, valid:0}` for CSV. |
