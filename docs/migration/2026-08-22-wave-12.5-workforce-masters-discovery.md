## B. Per-endpoint behaviour matrix

### B.1 `shifts` (`apis/api/shifts/*.php`)

| Endpoint | Lines | Behaviour worth porting exactly |
|---|---|---|
| `list.php` | 44 | Fixed predicate `is_active = 1 AND company_id = ?`. No search, no pagination, no filters. `ORDER BY created_at DESC, id DESC`. Explicit 8-column projection, `public_rows`. Message key `shifts`. |
| `one.php` | 46 | `(int) ($_GET['id'] ?? 0)`; falsy → `ID_REQUIRED` (400). Row must match id **and** `is_active = 1` **and** company. Miss → **`FORBIDDEN` at 404** — the message key is `forbidden` while the status is 404, matching D-060's uniform-404 shape. |
| `create.php` | 65 | `required(name, start_time, end_time)`; `assert_shift_daily_window_valid()`; INSERT with `days_off` defaulting to SQL NULL; re-read **by id only** (safe — just inserted); 201 `shift_created`. |
| `update.php` | 102 | Lookup by id + company but **not** `is_active`; miss → `SHIFT_NOT_FOUND` 404. Merged start/end from body-or-row; non-string → `INVALID_INPUT` 400; then the window assertion. `UPDATE ... COALESCE(?, col)` per column. Re-read, conditional notification, 200 `shift_updated`. |
| `delete.php` | 50 | Lookup by id + company, **not** `is_active`; miss → `SHIFT_NOT_FOUND` 404. Soft delete `is_active = 0`. `ok(SHIFT_DELETED)` with **no `data` key**. |

Four behaviours here are defects-as-specified and must be ported literally
unless the owner decides otherwise in §F:

1. **`COALESCE` makes `days_off` un-clearable.** `update.php:52-56` writes
   `days_off = COALESCE(?, days_off)`, so a JSON `null` — and an absent key —
   both preserve the old value. There is no request that sets `days_off` back
   to NULL once set.
2. **A soft-deleted shift is still updatable and still deletable.**
   `update.php:20-28` and `delete.php:26-34` scope by id + company only. A shift
   with `is_active = 0` is invisible to `list`/`one` but a `PUT` against it
   succeeds, returns it with `is_active: 0`, and can broadcast a notification.
3. **The notification fires on key presence, not on change.**
   `update.php:82-83` computes `$time_changed` as "`start_time` or `end_time` was
   supplied and non-null" — never comparing against the stored value. Re-sending
   the identical `start_time` broadcasts `SHIFT_TIME_CHANGED` to every employee
   in the company.
4. **The broadcast is not transactional.** `execute_query`, the re-read, and
   `notification_broadcast_company_employees` are three independent statements
   with no surrounding transaction.

`assert_shift_daily_window_valid()` (`apis/helpers/shift_times.php:47-60`):

- Regex `^(\d{1,2}):(\d{2})(?::(\d{2}))?$` — **the seconds group is captured and
  then never used**, so `09:00:59` and `09:00` are the same instant to this
  validator. Hours 0–23, minutes 0–59; anything else → `INVALID_INPUT` 400.
- `end > start` → same-day duration; `end == start` → duration 0 →
  `SHIFT_END_MUST_BE_AFTER_START` 400; `end < start` → overnight wrap
  `(1440 - start) + end`.
- Duration > 960 minutes → `SHIFT_EXCEEDS_MAX_HOURS` 400. A 16h00m shift is
  accepted; 16h01m is not.

|---|---|---|

Optional `search` on `name LIKE %..%`. `pagination_params()` + `pagination_meta()`. `ORDER BY created_at DESC, id DESC`. Message key `ok`. |

`request_type_bool_from_body()`
(`apis/helpers/request_actions_helper.php:270-278`) accepts exactly
`true`, `1`, `'1'`, `'true'` as 1; **everything else — including `'yes'`,
`'TRUE'`, `1.0` and `'on'` — is 0**, and an absent key is 0.

`request_type_exception_type_from_body()` (same file, `280-292`) returns NULL
unless `add_attendance_exception` is truthy by that same rule, then validates
the id against the company through `exception_type_validate_id_for_company()`
— the Wave 12.1 helper whose Java counterpart already exists.

### B.3 `company_official_holidays` (`apis/api/company_official_holidays/*.php`)

| Endpoint | Lines | Behaviour worth porting exactly |
|---|---|---|
| `list.php` | 54 | `SELECT *`. Optional `date_from`/`date_to` on `holiday_date` (via `!empty()`, so `0` is ignored), optional `search` on `name`. Pagination. `ORDER BY holiday_date ASC, id ASC` — the only ascending order in the wave. **Inverted authority gate, see §C.** |
| `one.php` | 27 | CA/HR + settings gate. `official_holiday_assert_company_row()`; miss → `NOT_FOUND` 404. |
| `create.php` | 76 | **Upsert over a date list.** Accepts `holiday_dates[]`, or a single `holiday_date`, or `dates[]` — in that precedence. Empty after normalization → `FIELD_REQUIRED` 400 with `field: holiday_dates`. Blank `name` → `FIELD_REQUIRED` 400 with `field: name`. Per date: existing `(company_id, holiday_date)` → UPDATE its name; otherwise INSERT. Returns **`public_rows(...)` — an array — at 201**, even when every date was an update and nothing was inserted. |
| `update.php` | 63 | Row by company; miss → 404. Name defaults to the stored name; blank → `FIELD_REQUIRED` 400. Date optional, `!empty()`-guarded, normalized; invalid → `INVALID_INPUT` 400 with `field: holiday_date`. Pre-checks the unique pair and answers **`INVALID_INPUT` at 409** on conflict. Then UPDATE scoped by id + company. |
| `delete.php` | 33 | CA/HR + settings gate. Row by company; miss → 404. Hard `DELETE` scoped by id + company. `ok(OK, null)` — an explicit null `data`. |

`official_holidays_normalize_dates()`
(`apis/helpers/official_holidays_helper.php`, the `function_exists`-guarded
block) does a strict `Y-m-d` round-trip via `DateTimeImmutable::createFromFormat`
and **silently skips** anything that fails, deduplicating by value and
preserving first-seen order. So `["2026-01-01", "not-a-date"]` creates one
holiday and reports no error at all; only an *entirely* invalid list produces
the `FIELD_REQUIRED` 400.

`create.php` is **not transactional**: each date is its own INSERT-or-UPDATE. A
failure on the fourth date leaves the first three committed and returns a 500.

## C. Authority matrix — three sibling modules, three different models

This is the single largest inconsistency in the wave and the reason §F.1 needs a
decision.

| Endpoint | Roles accepted | `can_company_settings` gate |
|---|---|---|
| `shifts/list` · `one` · `create` · `update` · `delete` | COMPANY_ADMIN, HR, MANAGER | **none, on any of the five** |
| `request_types/list` · `one` | **any authenticated role** (bare `requireAuth()`) | none |
| `request_types/create` · `update` | COMPANY_ADMIN, HR | none |
| `request_types/delete` | COMPANY_ADMIN, HR | **yes** |
| `company_official_holidays/list` | **any authenticated role** | **only when the role is CA or HR** |
| `company_official_holidays/one` · `create` · `update` · `delete` | COMPANY_ADMIN, HR | yes |

Two shapes deserve explicit attention:

**The inverted gate.** `company_official_holidays/list.php:16-20` reads:

```php
$settings_roles = [UserRoleEnum::COMPANY_ADMIN->value, UserRoleEnum::HR->value];
if (in_array($role, $settings_roles, true)) {
    require_company_settings_access($auth);
}
```

An EMPLOYEE or MANAGER lists holidays freely. An HR user **without**
`can_company_settings` is refused the same list. The privileged roles are the
restricted ones — the check is applied to exactly the roles that would otherwise
be trusted. This is almost certainly a bug in `hr-legacy`, and it is
observable: it changes who gets a 403.

**A create/delete asymmetry.** `request_types` lets any CA/HR user create and
update a type, but requires `can_company_settings` to delete one. `shifts` has
no permission gate at any verb, while an equally-destructive
`company_official_holidays/delete` has one.

**One Phase 1 boundary is already settled and needs no new decision.**
`require_company_settings_access()` (`apis/helpers/hr_permissions.php:170-174`)
only enforces when the session type is EMPLOYEE; a company-type session bypasses
it entirely. `LegacyHrPermissionEnforcer`'s class javadoc already records that
Phase 1 issues **only** employee-scoped legacy tokens (D-042), so the bypass has
no Phase 1 equivalent and the gate always applies. That is existing, documented
behaviour — carried forward, not re-decided here.

```text
company_official_holidays    (schema:244-250, indexes :1030-1033)
  id, company_id int UNSIGNED NOT NULL
  name           varchar(150) NOT NULL
  holiday_date   date NOT NULL
  created_at     timestamp NOT NULL DEFAULT current_timestamp()
  UNIQUE KEY uq_company_holiday_date (company_id, holiday_date)   <-- enforced
  KEY idx_company_holiday_range (company_id, holiday_date)
```

Three consequences:

1. **`shifts.company_id` is nullable.** Every endpoint in the module filters
   `company_id = ?`, so a row with a NULL company is invisible to `list`, `one`,
   `update` and `delete` alike — unreachable through the API but still joinable
   by Wave 12.6's assignment tables. See §E.2.
2. **`company_official_holidays` really does enforce the unique pair**, so
   `create.php`'s application-level upsert and `update.php`'s 409 pre-check are
   backed by a constraint. A concurrent create loses the race with a duplicate-key
   error rather than writing a duplicate row — which means the 409 path and the
   constraint path produce **different** responses for the same logical conflict.
3. **Neither `shifts` nor `request_types` constrains name uniqueness**, so
   duplicate names per company are legal and must stay legal.

`start_time`/`end_time` are MariaDB `TIME`, whose domain is
`-838:59:59 .. 838:59:59` — far wider than the validator's 00:00–23:59. Existing
rows may hold values the create/update paths would now reject, and `list`/`one`
must still render them.

## E. Tenancy and dirty-data questions

### E.1 `request_types/update.php` returns another company's row (needs a decision)

`update.php:53-59` scopes the write correctly:

```php
UPDATE request_types SET ... WHERE id = ? AND company_id = ?
```

but there is **no prior existence check**, and the re-read on line 61 is:

```php
$updated_row = get_one('SELECT * FROM request_types WHERE id=?', [$id]);
```

For an `id` belonging to another company the UPDATE matches zero rows — correct,
nothing is written — and then the re-read returns **that other company's row**,
which is serialized into a 200 response. A caller can enumerate ids and read
every company's request-type names and flags. Nothing is written, so this is a
confidentiality leak, not an integrity one.

`shifts/create.php` and `request_types/create.php` also re-read by id alone, but
those ids come from `get_last_inserted_id()` on the connection that just
inserted, so they are not exposed.

This is the same class of finding as D-060 (uniform 404) and D-075 (fail closed
on a foreign reference), both of which the owner resolved by **narrowing**.
§F.2 asks for the same call here.

### E.2 Company-less shifts

`shifts.company_id IS NULL` rows cannot be produced by `create.php`, which always
binds the session company. If any exist in production they predate the endpoint
or came from a migration. They are invisible to all five endpoints. **No J-query
was run to count them** — that would need production access this wave does not
have. Recorded as an open data question for the cutover checklist, not a
blocker: the port's behaviour (invisible) is identical to PHP's either way.

### E.3 Existing `TIME` values outside 00:00–23:59

Same shape: `list`/`one` render whatever is stored; `update` re-validates the
merged window and would reject such a row if the caller supplied either time.
Ported behaviour matches PHP exactly, so this needs no decision — only a note in
the cutover checklist.

### E.4 Holidays whose name is blank

`create.php` and `update.php` both reject a blank name, but the column is only
`NOT NULL` — `''` is storable and pre-existing rows may hold it. `list`/`one`
render it unchanged; `update.php:31-34` **defaults to the stored name and then
rejects it**, so a legacy row with a blank name cannot be updated at all until
the caller supplies a name. Literal port; no decision needed.

## F. Owner decisions required before implementation

### F.1 The three-way authority inconsistency — and the inverted holidays gate

Wave 12.4 set the precedent (D-076): where legacy's authority model is
demonstrably wrong, the owner chose to **narrow** rather than reproduce, and
recorded it as an explicit divergence using legacy's own `forbidden` key.

Three questions, which can be answered independently:

1. **`shifts` has no permission gate on any verb**, while the comparably
   destructive `company_official_holidays/delete` and `request_types/delete` do.
   Reproduce as-is, or gate the `shifts` mutations on `can_company_settings`?
2. **`company_official_holidays/list`'s inverted gate** refuses HR users without
   `can_company_settings` while serving EMPLOYEE and MANAGER freely. Reproduce
   as-is, or drop the gate on `list` so the privileged roles are not the
   restricted ones?
3. **`request_types/list` and `one` accept any authenticated role.** Reproduce,
   or align with the CA/HR/MANAGER shape `shifts` uses?

My recommendation, for the same reason D-076 was accepted: reproduce (1) and (3)
literally — they are permissive but coherent, and narrowing them would break
mobile clients that read request types as an employee — and **fix (2)**, because
it is incoherent in both directions and cannot be what was intended. That would
be one narrow, tested divergence rather than three.

### F.2 The `request_types/update.php` cross-tenant read

Options:

- **(a) Reproduce literally** — a foreign id returns that company's row at 200.
- **(b) Fail closed like D-075** — check the row exists for the company first and
  answer `NOT_FOUND` 404, matching `one.php` and `delete.php` in the same module.
- **(c) Scope the re-read** — `WHERE id = ? AND company_id = ?`, then answer 404
  when it comes back empty.

(b) and (c) are behaviourally identical for a foreign id and differ only in
statement count. I recommend **(b)**: it makes `update` consistent with the two
sibling endpoints that already do exactly this, and it is the narrowest change
that closes a cross-tenant read.

### F.3 Notification-on-no-change for shifts

`shifts/update.php` broadcasts to every employee in the company whenever
`start_time` or `end_time` is *present* in the body, even if identical to the
stored value. Reproduce literally, or compare against the stored value first?

Reproducing is the D-082-consistent answer (the notification call boundary is a
seam, not a behaviour we redesign), and I recommend it — but it is worth an
explicit yes, because a chatty client could broadcast to an entire company on
every save.

### F.4 Wave boundary for `official_holidays_helper.php`

That helper is 250 lines, and **only two of its functions are used by this
wave's endpoints**: `official_holidays_normalize_dates()` and
`official_holiday_assert_company_row()`. The rest —
`official_holidays_count_in_range/month`, `..._working_days_in_range`,
`..._credit_days_for_employee`, `..._working_credit_details_for_employee`,
`..._working_credit_for_employee`, `official_holidays_is_weekly_rest_day` — are
consumed by attendance (12.6) and payroll (12.8/12.9), and several depend on
`company_setting_values`, which D-4 moved to **item 13**.

I propose porting **only the two in-scope functions** in this wave and leaving
the consumers to the waves that call them. Confirming this keeps 12.5 from
pulling item 13's dependency forward.
