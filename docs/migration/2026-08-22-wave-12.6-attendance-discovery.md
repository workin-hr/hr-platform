Three consequences worth stating now:

1. **`attendance` has no unique constraint at all.** Duplicate check-ins are

2. **`employee_schedules` enforces one row per employee per day**, so

3. **Deleting a shift cascades into `employee_shift_assignments`.** Wave 12.5's
   `shifts/delete.php` is a *soft* delete, so this cascade is not reachable
   through that endpoint — but it is reachable through
   `company_delete_helper.php`, and it means a hard shift delete silently
   unassigns employees.

| `list` | `DATE()`, `TIMESTAMPDIFF`, `date()`, `new DateTime`, `strtotime` |
| `overall_report` | `date()` |
| `stats` | `DATE()`, `TIMESTAMPDIFF`, `date()`, `strtotime` |
| `update` | `date()`, `strtotime` |
| `employee_monthly_schedule` | `date()` |

This is qualitatively worse than earlier waves, for one reason:

**`check_in.php:56` writes the attendance timestamp with `NOW()`** — the
database decides when the employee checked in — while **`check_in.php:63`
reports `date('Y-m-d H:i:s')`**, the application clock. A single response
therefore mixes two clocks: the row's `check_in` comes from the database session
timezone, and the `time` field the client is shown comes from `LegacyClock`.
Until D-083 is closed those two disagree by the offset difference, in a value a
client displays to the employee.

The 2-hour duplicate guard (`check_in.php:35`) is also evaluated with `NOW()`,
so the window itself moves with the session timezone.

**D-083 is not closed by this wave and no `SET time_zone` is proposed.** It is
recorded here as materially more urgent than it was: earlier waves exposed
timezone-sensitive *reads*; this wave has timezone-sensitive **writes** whose
values become permanent rows.

## F. Check-in / check-out / QR map

### F.1 `check_in.php` — statement order

```text
method guard -> requireAuth() (any role) -> requireCompanyActive
-> body(); required(latitude, longitude, method)
-> employee_id = body.employee_id ?? auth.employee_id ?? 0   <-- see I.1
-> employee lookup scoped by id + company_id  (404 invalid_employee)
-> is_self_attendance = auth.type === 'employee' && auth.employee_id === employee_id
-> if (is_self_attendance && empty(is_mobile_attendance_enabled)) 403
-> attendance_find_open_session(employee_id)  -> already_checked_in
-> last check-in; TIMESTAMPDIFF(MINUTE, last, NOW()) < 120 -> 422
-> if (!empty(lat) && !empty(lng)) validate_employee_attendance_location(...)
-> INSERT ... VALUES (?, NOW(), ?, ?, ?)
-> ok(check_in_recorded, {attendance_id, time: date('Y-m-d H:i:s')})
```

No transaction anywhere. The open-session probe, the 2-hour probe and the INSERT
are three independent statements, so two concurrent requests can both pass the
probes and both insert — and there is no unique constraint to stop them (§D.1).

### F.2 Behaviours that must be ported literally

- **`required()` passes `"0"`, `!empty()` does not.** `latitude` and `longitude`
  are `required`, then geofence validation is guarded by
  `!empty($lat) && !empty($lng)`. A check-in at latitude `0` or longitude `0`
  therefore passes `required()` and **skips location validation entirely**. See
  §I.2.
- **The 422 carries a hard-coded Arabic string**, not a lang key:
  `'لا يمكن تسجيل بصمتين متتاليتين خلال اقل من ساعتين'` (`check_in.php:38`). It
  is returned as `Response::REASON` and is not translated for an English client.
- `method` is in `required()`, so the `?? AttendanceMethodEnum::APP` fallback on
  the INSERT is **dead code**. Reproduce the fallback anyway or drop it — it
  cannot change behaviour either way, and this document flags it so a reviewer
  does not read its absence as a defect.

### F.3 `check_in_qr.php`

QR is validated against **`branches.qr_code` plus an expiry**, scoped by
`company_id` (`check_in_qr.php:23-38`); a miss is `invalid_qr`. The matched
branch id becomes the attendance branch context. The insert records
`method = 'qr'`. No token, nonce or signature is involved — the QR value is a
stored column, so it is a **bearer secret with no replay protection** beyond its
expiry. Recorded as an observation, not a proposed change.

### F.4 `attendance_find_open_session()` — a hidden write, fully traced

This was previously deferred to implementation time. That was wrong: it mutates
rows, so it is part of the endpoint contract. Traced in full
(`apis/helpers/attendance_session_helper.php`):

```text
attendance_find_open_session(employee_id, full_row = false)          :170
  1. employee_id <= 0                     -> null, no query
  2. company_id = attendance_employee_company_id(employee_id)        :191
        SELECT company_id FROM employees WHERE id = ?
  3. if company_id > 0:
        attendance_auto_close_stale_open_sessions(company_id, employee_id)   <-- WRITE
  4. SELECT id, check_in, latitude, longitude, exception_type_id
       FROM attendance
      WHERE employee_id = ? AND check_out IS NULL AND check_in IS NOT NULL
      ORDER BY id DESC LIMIT 1
  5. blank check_in                       -> null
  6. attendance_is_exception_only_row(...) -> null   (synthetic rows stay open)
  7. company_id <= 0                      -> return row
  8. deadline = attendance_open_session_deadline(company_id, employee_id, check_in)
     if (new DateTimeImmutable('now') >= deadline):
        attendance_auto_close_stale_open_sessions(...) AGAIN               <-- WRITE
        -> null
  9. return row
```

`attendance_auto_close_stale_open_sessions()` (`:80`) is the write:

```text
  SELECT id, check_in, exception_type_id FROM attendance
   WHERE employee_id = ? AND check_out IS NULL AND check_in IS NOT NULL
   ORDER BY id ASC
  foreach row:
     blank check_in                    -> continue
     attendance_is_exception_only_row  -> continue
     deadline = attendance_open_session_deadline(...)
     asOf < deadline                   -> continue
     checkInTs = strtotime(check_in)
     dateYmd   = date('Y-m-d', checkInTs)
     expected  = attendance_import_expected_for_day(company_id, employee_id, dateYmd)
     worked    = max(0, expected_minutes - ATTENDANCE_INCOMPLETE_PUNCH_DEDUCTION_MINUTES)
     checkOutAt = date('Y-m-d H:i:s', checkInTs + worked * 60)
     UPDATE attendance SET check_out = ?
      WHERE id = ? AND check_out IS NULL                                   <-- WRITE
```

#### What this means for the contract

- **`check_in.php`, `check_in_qr.php` and `check_out.php` can all mutate older
  attendance rows before performing their own operation**, because each calls
  `attendance_find_open_session()` before its main write.
  `employee_monthly_attendance.php` does too, on a **GET**.
- The synthetic `check_out` is **computed, not observed**: it is
  `check_in + (expected_minutes - deduction)`, so it fabricates a plausible
  departure time rather than recording one. Those rows are indistinguishable
  from real check-outs in the schema.
- The write loop is **unbounded** — every stale open row for that employee is
  closed, not just the latest — and there is **no transaction**. A failure
  part-way leaves some rows closed.
- The `UPDATE ... AND check_out IS NULL` guard is the only concurrency
  protection, and it is per-row.
- **Clock semantics are mixed inside one function.**
  `new DateTimeImmutable('now')` and `date()` are the *application* clock
  (`LegacyClock`, +02/+03); the `check_in` values they are compared against were
  written by the *database* with `NOW()`. D-083 therefore does not merely shift
  displayed values here — it decides **whether a row gets auto-closed at all**,
  and what synthetic `check_out` is stored.
- `attendance_open_session_deadline()` (`:40`) walks **up to 8 days forward**
  looking for the next non-rest day, calling
  `attendance_import_expected_for_day()` once per candidate day — so a single
  `find_open_session` can issue many queries and reaches the frozen helpers
  described in §G.

**A GET that writes.** `employee_monthly_attendance.php` is a read endpoint whose
first act can be to close attendance rows. Any Java port that treats GETs as
read-only — a read-only transaction, a replica route, a caching layer — breaks
this. Recorded here so it cannot be discovered late.

### G.1a Correction — `import_excel`'s endpoint closure is not its helper closure

The §G.1 matrix was computed from each endpoint's helper call closure, and on
that basis reported `import_excel` as clean. That is correct about the
**helper** and incomplete about the **endpoint**:

| Closure | Reaches |
|---|---|
| `attendance_excel_import_punch_log()` | 29 functions across `attendance_excel_analyzer.php`, `xlsx_parser.php`, `functions.php`, `db_query.php`, `org_hierarchy.php`. **None** of `attendance_import_expected_for_day`, `company_setting_selected_values`, `schedule_is_weekly_rest_day`, `payroll_is_weekly_rest_day` |
| `import_excel.php` itself | all of the above, **plus** `attendance_excel_import_is_available()` → `attendance_excel_import_available_from()` → `app_config_value('attendance_excel_import_available_from')` → the **`configs`** table |

**This does not invalidate slice 1b's separability.** The `configs` read is a
narrow availability gate on a single key, not the frozen `company_settings` /
payroll weekly-rest closure that blocks `analyze_excel`. `configs` is also
already read by the delivered port — `LegacyClock` issues the identical
`SELECT config_value FROM configs WHERE config_key = ? LIMIT 1` — so no new
boundary is crossed and no decision is required. It is recorded here because
the dependency belongs in the endpoint's row and was missing from it.

`app_config_value()` semantics that must be preserved (`configs_helper.php:7-30`):
a **per-request static cache** keyed by config key; a SQL failure caches null
and returns the caller's default; a missing row or a null value caches null; a
non-blank value is trimmed and cached; a blank value caches null. The cache is
observable here, because the unavailable path reads the same key **twice** —
once through `attendance_excel_import_is_available()` and again through
`attendance_excel_import_available_from_display()` to build the `{date}`
replacement. Java must therefore observe **one request-stable value**, not two
independent reads that could disagree mid-request.

`attendance_excel_import_is_available()` compares against
`new DateTimeImmutable('today')` — the application clock, which
`LegacyClock.today()` already reproduces. That is not a new D-083 dependency,
and no session-timezone change is authorised.

#### `parse_ymd_config_date()` rolls; it does not validate

Measured under PHP 8.3 (`Etc/GMT-2`). The helper calls
`DateTimeImmutable::createFromFormat()` with `'!Y-m-d'` then `'!Y-n-j'` and
**never inspects `getLastErrors()`**, so out-of-range components roll forward
instead of failing:

| input | PHP result |
|---|---|
| `2026-01-15` | `2026-01-15 00:00:00` |
| `2026-1-5`, `2026-1-15`, `2026-01-5` | correct date at midnight (the `Y-n-j` fallback) |
| **`2026-02-30`** | **`2026-03-02`** — rolled, not null |
| **`2026-13-01`** | **`2027-01-01`** — rolled, not null |
| `garbage`, `""` | null |
| `"  2026-01-15  "` | `2026-01-15` — trimmed before parsing |

A strict `LocalDate.parse` would answer null where PHP answers a rolled date,
and the availability gate would then refuse an import PHP admits. The port must
roll.

### G.1b Correction — the punch parser is its own grammar, not `strtotime`

§I.4 recorded that the attendance spreadsheet stack shares nothing with Wave
12.4's. That holds, and one consequence needs stating outright because it is
easy to get wrong in the other direction:
`attendance_import_parse_punch_datetime()` (`attendance_excel_analyzer.php:189`)
is **not** implemented by calling `strtotime()`, and must not be ported as a
call to `LegacyPhpStrtotime`. Its source order is:

1. numeric / Excel-serial branch, taken when the value is numeric and `> 1000`;
2. `trim`;
3. remove `U+200E`, `U+200F`, `U+FEFF`;
4. strip a trailing device suffix such as `A4P4` — **only** when the value does
   not end in `AM`/`PM`;
5. rewrite backslash to forward slash;
6. normalise a dotted **date prefix** (`18.07.2026`) without touching a time
   (`10:20:24`);
7. try an explicit format list **in source order**;
8. **only then** fall back to `strtotime()`.

The explicit formats are **day-first** — `d/m/Y h:i:s A`, `d/m/Y h:i A`,
`d-m-Y h:i:s A`, `d/m/Y H:i:s`, … — whereas D-094's bounded grammar reads a
slashed three-part value the American way (`01/15/1990` is measured as 15
January). Running a punch log through the general parser first would therefore
**transpose day and month on every ambiguous date**. Slice 1b implements a
helper-local parser preserving the order above, with `LegacyPhpStrtotime` used
only as step 8's fallback; D-094's grammar is not broadened to absorb it.

**Excel serial conversion is reused, and the reuse is proven.** PHP's
`excel_serial_to_datetime_string()` (`xlsx_parser.php:334-345`) and Wave 12.4's
`LegacyXlsxReader.excelSerialToDateTime()` are the same computation: epoch
offset 25569, no phantom-1900 correction, fractional part scaled to time,
`gmdate`/UTC formatting, and the conditional `Y-m-d` vs `Y-m-d H:i:s` output. A
differential test pins serials 1, 59, 60, 61, 25569, 25569.5 and 45000.25
against the measured PHP output; all seven agree, so no second converter is
added.

## I. Dirty-data, tenancy and security findings

### I.1 Attendance on behalf of another employee — corrected

`check_in.php:18` takes the target from `body.employee_id ?? auth.employee_id`
under a bare `requireAuth()`. The employee is looked up by id **and company**, so
this is not cross-tenant; within a company it is a privilege gap, and the three
endpoints do **not** share one mechanism:

- **`check_in.php`** computes
  `is_self_attendance = auth.type === 'employee' && auth.employee_id === employee_id`.
  Targeting a colleague makes it **false**, which *skips* the
  `is_mobile_attendance_enabled` check at `:26` and passes
  `$is_self_attendance = false` into
  `validate_employee_attendance_location()`, relaxing the geofence rule for that
  call.
- **`check_out.php`** uses the same `is_self_attendance` mechanism.
- **`check_in_qr.php` accepts the supplied target too, but has no
  `is_self_attendance` variable and no mobile-attendance check at all.** There is
  nothing for acting-on-behalf to bypass there, because the restriction does not
  exist on that endpoint in the first place. The earlier wording lumped all three
  together and was inaccurate.

### I.2 Latitude or longitude of exactly zero disables geofencing

`required()` accepts `"0"`; `!empty("0")` is false. A caller sending
`latitude: 0` (or `"0"`, or `0.0`) satisfies the required-field contract and then
skips `validate_employee_attendance_location` entirely. Null Island is a real
coordinate.

### I.3 `attendance` has no unique constraint

Two concurrent check-ins can both pass the open-session and 2-hour probes and
both insert — no transaction, no constraint. Legacy has the same race.

### I.4 Spreadsheet surface shares nothing with Wave 12.4

`attendance_excel_analyzer.php` reaches `xlsx_parser.php` and `schedule_helper`,
and does **not** use the employee spreadsheet helper. Wave 12.4's
`LegacyEmployeeSpreadsheet*` stack, its 28-column metadata and its D-085 reader
corrections are **not** transferable on the strength of matching filenames. Only
the format primitives are reuse candidates, each justified against
`xlsx_parser.php`.

### I.5 Notification side effects

`attendance/import_excel.php` and `schedules/assign_employee_schedule.php` only.
Both land on the D-082 boundary; hr-platform#22 still owns delivery.

#### K.0.1 `PDOException` is a `RuntimeException` — SQL failures are 400

The first cut classified database failures as D-084 generic 500s. That is not
PHP's catch hierarchy, and the endpoint's own control flow says so:

```php
} catch (RuntimeException $e) {
    $pdo->rollBack();
    $key = $e->getMessage();
    if (is_string($key) && str_starts_with($key, 'attendance_excel_')) {
        fail($key, 400);
    }
    fail(LangKey::INVALID_FILE_TYPE, 400, $key);
} catch (Throwable $e) {
    $pdo->rollBack();
    throw $e;
}
```

`apis/config/pdo.php:15` sets `PDO::ERRMODE_EXCEPTION`, and in PHP
**`PDOException extends RuntimeException`**. So a MariaDB constraint error
raised by `$pdo->prepare(...)->execute(...)` is claimed by the **first** catch:
rollback, then `invalid_file_type` **400** with the exception message in
`data`. Confirmed by probe rather than by reading — `is_subclass_of` reports
true, and the create-mapping INSERT lands in the first catch under both a
permissive and a strict `sql_mode`.

**Measured, PHP 8.3 + mysqlnd against MariaDB 11.8**, for the create-mapping
INSERT with `branch_id` NULL:

| field | value |
|---|---|
| HTTP status | **400** |
| message key | `invalid_file_type` → *"Invalid file type"* |
| `data` | `SQLSTATE[23000]: Integrity constraint violation: 1048 Column 'branch_id' cannot be null` |
| SQLSTATE | `23000` |
| MariaDB error | `1048` |

**The corresponding JDBC**, MariaDB Connector/J 3.5.8 against the same server
and the same statement:

| field | value |
|---|---|
| class | `java.sql.SQLIntegrityConstraintViolationException` |
| `getSQLState()` | `23000` |
| `getErrorCode()` | `1048` |
| `getMessage()` | `(conn=5) Column 'branch_id' cannot be null` |

The server text is **identical**; Connector/J only prefixes `(conn=N)` and a space. PDO's
message is therefore fully reconstructible as
`SQLSTATE[{state}]: {description}: {code} {server text}`, and the one part with
no JDBC counterpart — the description — was **extracted by measurement** rather
than transcribed, by raising each state through MariaDB's `SIGNAL SQLSTATE` and
reading PDO's message back. 37 states were captured that way, *including the
miss*: a state PDO does not know renders literally as `<<Unknown error>>`
(measured on `ZZZZZ`, `99999`, `XX999`, `45000`, `70100` and `XA100`). So every
input has a measured answer and nothing is invented.

Implemented as `com.workin.legacy.LegacyPdoException`, a dedicated
compatibility type meaning *"PHP would have called this a `RuntimeException`"*.
**Every other Java `RuntimeException` keeps its D-084 treatment** — the
distinction the review asked for, and the reason this is not a blanket
`catch (RuntimeException)`. A second test drives a foreign-key failure (`1452`)
through the same path, so what is pinned is the reconstruction and not one
memorised string.

**Rollback and commit semantics** are now literal too:

- `getDB()` and `beginTransaction()` sit **above** the try in PHP, so a failure
  in either is uncaught and stays D-084. They are outside the mapped region here.
- `commit()` is **inside** the try, so a commit `PDOException` is a 400 on the
  same branch as any other.
- `rollBack()` is called inside the catch body with **no nested catch**. A
  rollback that itself throws therefore escapes and masks the mapped failure.
  Reproduced: the rollback is not swallowed, so a parser 400 cannot survive a
  transaction that would not roll back.

#### K.0.2 The newly evidenced `strtotime()` families are closed

D-094's follow-up is activated by this endpoint, and the two families it
evidenced are now implemented in `LegacyPhpStrtotime` rather than reported:

| family | grammar added |
|---|---|
| clock time, no date | `H:i`, `H:i:s`, `h:i A`, `h:i:s A`; `:` and `.` interchangeable and mixable |
| month-name date | `d M`, `d M Y`, `M d`, `M d Y`, `M d, Y`, `M`, `M Y`, each with an optional trailing time |

Bounded by measurement, not by example. The rules a tidier grammar would have
got wrong, all probed:

- **the fields do not share a rule.** Hour 24 is legal and rolls (`24:01` is
  00:01 tomorrow), hour 25 is not; minute 60 is rejected outright; second 60 is
  the leap second and rolls a minute, while 61 is rejected;
- **a one-digit minute is tens-less**: `11:5` is 11:05, not 11:50;
- **a meridiem tightens everything**: the hour becomes 1–12 (`00:03 AM` and
  `13:03 PM` are both false) and the minute and second must be two digits, so
  `1:5 PM` is false where a bare `11:5` is not;
- **seconds default to zero**, not to the reference second;
- **short years follow the 69 boundary** (`26 Apr 69` is 2069, `26 Apr 70` is
  1970), and a three-digit token goes through the same rule, so `026` is 2026;
- **an asymmetry that is real**: `Apr 26 08:03` parses and `26 Apr 08:03` does
  not, because in the day-first order PHP consumes the following bare number as
  the *year* and is then left with `:03`. The implementation reproduces the
  asymmetry rather than smoothing it, and a test names it;
- **a bare month keeps the reference day** and rolls: `Apr` against a 31st is
  1 May, while `Apr 2026` is the 1st.

The endpoint ordering is unchanged: punch preprocessing → the sixteen explicit
`createFromFormat` formats → `LegacyPhpStrtotime`. The day-first formats still
win before the general parser.

**One narrower exclusion remains, and it is D-094's existing one.** PHP reads a
trailing lone `a` as the military timezone UTC+1, so `08:03 a` is
`2026-08-22 09:03:00` — an hour off "8am" — and `26 Febr` is `Feb` plus `r`.
Timezone-suffix tokens were **not** added, per standing instruction. Reachable
only from a value ending in a *single* trailing letter, since two or more
alphanumerics are removed as a device suffix first.

A by-product worth recording, because it looks like a port bug and is not: the
device-suffix strip **destroys the year**. `26 Apr 1990` loses `" 1990"` and
comes back as 26 April **2026**, the reference year. Add a time and the year
survives, because the last token is then a clock rather than a bare number.
Both measured; both pinned.

#### K.0.3 Excel 97-2003 (`.xls`) — delivered under D-097

**Closed.** D-097 accepted Apache POI HSSF as the structural reader for the
BIFF8 surface `parse_legacy_xls_spreadsheet()` documents, and `.xls` now
imports. Exactly one dependency was added —
`implementation 'org.apache.poi:poi:5.5.1'` — and `poi-ooxml` is deliberately
absent, because the XLSX path was already ported. `LegacyXlsxReader` and
`LegacyCsvReader` are untouched and remain authoritative for their formats;
POI is reachable only under `LegacySpreadsheetFormat.XLS`.

**The adapter is `LegacySimpleXlsReader`, and its job is narrow.** POI supplies
structure — OLE2 container, BIFF records, the shared string table, the
`XF`/`FORMAT` tables, the date window — and every value that leaves the class
is rendered by `SimpleXLS`' own rules. `DataFormatter` is never called. The
rules ported are `$numberFormats`, `$dateFormats`, the unconditional
`$datetimeFormat`, the `NINETEENFOUR` epoch, and the classification in
`isDate()` that chooses between them.

Three of those rules are load-bearing rather than cosmetic:

- **a date cell always carries a time half.** `$datetimeFormat` is
  unconditional, so a whole-day serial is `2026-04-26 00:00:00` — where the
  XLSX-side `excel_serial_to_datetime_string()` would answer `2026-04-26`. The
  shared helper is therefore *not* reused; a separate `createDate()` is
  implemented and differentially pinned.
- **the epoch is skipped for serials at or below 1.** A time-only cell holding
  `0.5` is not a time of day at all: it is `1970-01-01 12:00:00`. Measured in
  both date windows, which is what proves it is a skip and not a different
  subtraction.
- **a numeric cell goes through `sprintf`.** A code in a `0.00`-formatted cell
  is `"555004.00"`, and the punch-log guard is `preg_match('/^\d+$/')` — so
  rendering it as POI's `555004` would silently import a sheet legacy rejects.

Two rounding rules had to be measured rather than assumed, and they disagree
with each other. `sprintf('%1.0f', 2.5)` is **`"2"`** — PHP formats through
`zend_dtoa` and rounds the exact binary value **half to even**, which is the
opposite of `String.format`. But `round()` inside `createDate()` rounds **half
away from zero**. Both are implemented as measured; a mutation to either is
caught.

**The `.xls` branch of `attendance_import_load_rows()` is not the shared
path**, and the difference is now reproduced. It is a separate early return: it
uses the wrapper's own header handling, which drops any row with fewer than two
non-blank cells; it has no `'empty'` short-circuit; and its
`unknown -> punch_log` fallback is **unconditional**, where the CSV/XLSX path
applies it only to a sheet with exactly two non-blank columns. A three-column
`.xls` therefore arrives as `punch_log` and fails the two-column check, while
the same three columns as CSV are `unknown` and fail as an unsupported format.

**The success envelope keeps legacy's oddity.** `$is_xlsx_import = $format ===
'xlsx'`, and `.xls` is not `'xlsx'`, so a successful workbook import answers
`imported_csv` with a `{count}` placeholder — a different key *and* a different
placeholder from the XLSX branch, for identical rows. Pinned by an HTTP test.

**Encrypted workbooks are refused deliberately.** Left alone POI tries Excel's
well-known default password unprompted and would open a workbook legacy cannot
read; the adapter installs a password that cannot match for the duration of the
parse. What that produces is *not* the response one would guess — see §K.0.5.

**D-097's divergence, both sides measured.** A pre-97 workbook is parsed by
`SimpleXLS` through its incidental `BIFF7 = 0x500` branch and refused here with
`invalid_file_type` 400 and `data` = `Cannot read XLS file. Invalid or
corrupted file`. Two markers can carry the old format and the two readers check
different ones — `SimpleXLS` accepts either the `Workbook` or the `Book` stream
name and then dispatches on the `BOF` version, while POI keys its
`OldExcelFormatException` on the `Book` stream name and does not mind the
version. So the adapter gates on the version explicitly and POI's own check
stands behind it; a fixture exercises each.

```text
currency          99.5            custom \-   2026-04-26 12:00:00   2030-04-27 12:00:00
percent           8%              custom /    2026-04-26 12:00:00   2030-04-27 12:00:00
percent decimals  7.50%
custom non date   1234.5678
text format       555004
half up           2               <- sprintf rounds half to EVEN
big               1.0E+20         <- PHP's 14-digit float precision
```

`serial 60` is Excel's phantom 29 February 1900, uncorrected on both sides — the
same behaviour `LegacyExcelSerialDifferentialTest` already pins for XLSX.

**What POI cannot write, and how it is covered.** HSSF writes `NUMBER` and
`BLANK` records and offers no way to ask it for `RK`, `MULRK` or `MULBLANK`.
Those are **not** a formatting variant of `NUMBER`, so testing the renderer over
`NUMBER` cells would have proven only post-decoding formatting:
`SimpleXLS::parseSheet()` decodes an `RK` through its own `getIEEE754()`, with
its own XF lookup, date check, multiplier and `sprintf`, and walks a `MULRK` run
with hand-written offset arithmetic — a six-byte stride, the value at
`tmppos + 2`, the XF the date check reads four bytes earlier, and the last
column taken from the record's final two bytes rather than from a count.

So the last three fixtures rewrite the cell records of a POI-written workbook at
the byte level, and a test asserts the committed bytes really carry sid `0x027E`
/ `0x00BD` / `0x00BE` and no longer carry `NUMBER` or `BLANK` — otherwise a
rewrite that silently stopped matching would leave the assertions passing over
ordinary cells and proving nothing. Every row matched PHP on the first run, so
**no production change was made**.

| fixture | covers | PHP | Java |
|---|---|---|---|
| `rk` | all four `RK` encodings: 30-bit signed integer and top-30-bits-of-double, each with and without the `/100` flag; both signs; both range ends; General, `0.00` and date format indices | 15×2 grid, 14 assoc rows | same |
| `mulrk` | two runs of three adjacent packed cells, each cell carrying a *different* XF | 3×4 grid, 2 assoc rows | same |
| `mulblank` | a two-cell blank run between filled cells | positions stay `''` | same |

`rk date and time` renders `2026-04-26 06:00:00`, not the `08:03` its serial was
built from: the double encoding keeps 21 mantissa bits, so the time half is
genuinely lost **in the file**. Both readers decode the same truncated bits,
which is the point.

One record is deliberately out of scope. `SimpleXLS` also accepts the pre-BIFF8
`0x007E` spelling of `RK` alongside BIFF8's `0x027E`; POI knows only `0x027E`.
No BIFF8 writer emits `0x007E`, and D-097 scopes this surface to BIFF8, so it is
recorded here rather than tested — it is a pre-97 concern, not a BIFF8 one.

#### K.0.5 Two malformed-input cases — accepted under D-098

The review asked for corrupt, encrypted and non-workbook inputs to be mapped to
"the measured SimpleXLS error envelope". Measurement found that for two of the
three **there is no envelope**, and for the third the envelope is not the one it
appears to be. All three were measured; none is guessed.

- **Encrypted BIFF8 → `[]`, and the response is *not* `invalid_file_type`.**
  `parseEntries()` returns `false` the moment it sees `FILEPASS`, but it never
  calls `error()` — so `parseFile()` still reports success, `rows()` finds no
  sheet, and the wrapper returns an empty array. An empty sheet has no columns,
  so the punch-log resolver rejects it with **400
  `attendance_excel_must_have_two_columns`** long before anything decides the
  file was unreadable, and the response carries **no `data` key at all** -- not
  a null one. Java reproduces that exactly, and D-098 explicitly excludes it.
  Flagged because the review expected the unreadable-XLS path; parity was
  chosen over the expectation, per ADR-0011 and D-058.
- **Truncated BIFF8 → does not terminate.** `parseSheet()` walks off the end of
  the workbook stream and keeps going four bytes at a time, warning on every
  read; it had not finished after **two minutes** on a 3KB file and has no
  bound. In a request it dies on `max_execution_time`.
- **Valid OLE2 with no `Workbook` stream → PHP fatal.** `readWorkBook()`
  dereferences an unset property index and grows a string until the 128MB
  memory limit is exhausted: `Fatal error: Allowed memory size of 134217728
  bytes exhausted`.

Neither of the last two can be reproduced, and neither should be: reproducing
them would preserve a denial-of-service failure mode rather than application
compatibility. Both are answered with the bounded `invalid_file_type` 400 and
`Cannot read XLS file. Invalid or corrupted file` — a message legacy *can*
produce from this wrapper, so the wire shape is not a new one.

**Owner disposition accepted under D-098**, which is limited to exactly those
two cases and required no production change: the bounded exception path
delivered with D-097 already implements it. The encrypted case above is
deliberately **not** D-098 — it keeps measured PHP parity and must not be moved
onto the invalid-file path.

### K.2 D-093 coordinate edge cases — to be resolved before 12.6.3

`required($body, [LATITUDE, LONGITUDE, METHOD])` runs first
(`check_in.php:16`); the geofence call is guarded separately at `:45`. The two
answer different inputs, and D-093 changes only the second. Each row states
which answers first; **the "after D-093" column is the intended behaviour and is
to be confirmed against source before implementation, not treated as settled by
this table.**

| `latitude` value | `required()` verdict | Legacy geofence invoked? | After D-093 |
|---|---|---|---|
| key absent | **fails** — `!isset` | never reached | unchanged: `field_required` |
| JSON `null` | **fails** — `isset(null)` is false | never reached | unchanged: `field_required` |
| `""` | **fails** — `=== ''` | never reached | unchanged: `field_required` |
| `"0"` | passes | **no** — `!empty("0")` is false | **yes** — validation runs |
| numeric `0` | passes | **no** — `!empty(0)` is false | **yes** — validation runs |
| `0.0` | passes | **no** — `!empty(0.0)` is false | **yes** — validation runs |
| non-numeric string (`"abc"`) | passes | **yes** — non-empty | unchanged: validation runs; `(float)` casts to `0.0` |
| valid positive (`30.0444`) | passes | yes | unchanged |
| valid negative (`-0.1276`) | passes | yes | unchanged |

Three points the matrix makes visible:

- The three genuinely-absent cases are all answered by `required()` **before**
  the geofence guard is reached, so D-093 cannot affect them. A missing
  coordinate still fails the same way it does today.
- D-093's entire effect is the three zero-valued rows.
- `"abc"` already reaches validation today and is cast to `0.0` by `(float)`,
  which means legacy already validates a garbage coordinate as Null Island while
  refusing to validate an honest one. That asymmetry is the clearest argument
  that the truthiness guard was never a deliberate rule.
