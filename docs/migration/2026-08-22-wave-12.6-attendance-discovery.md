## C. Tenancy — no table in this wave has a `company_id`

```text
attendance                  (schema:121-132)   employee_id -> employees
employee_schedules          (schema:455-464)   employee_id -> employees
employee_shift_assignments  (schema:476-484)   employee_id -> employees, shift_id -> shifts
```

All three are **employee-derived tenancy** (P-1b), the policy Wave 12.2 built and
Wave 12.4 first exercised at scale. There is no direct-company predicate
available anywhere in the wave; every endpoint must reach `employees.company_id`
through a join or a prior lookup. `attendance/list.php` does this with
`$company_id` bound into a subquery at lines 43, 133 and 277.

## D. Schema, FK and index matrix

| Table | Unique | Indexes | FK behaviour |
|---|---|---|---|
| `attendance` | **none** | `fk_attendance_employee`, `index_employee_date (employee_id, check_in)`, `fk_attendance_exception_type` | `employee_id` → `employees` **ON DELETE CASCADE**; `exception_type_id` → `exception_types` **ON DELETE SET NULL** |
| `employee_schedules` | **`uniq_employee_schedule_date (employee_id, schedule_date)`** | `fk_employee_schedule_employee` | `employee_id` → `employees` **ON DELETE CASCADE** |
| `employee_shift_assignments` | **none** | `idx_esa_employee`, `idx_esa_shift`, `idx_esa_employee_effective (employee_id, effective_from)` | `employee_id` → `employees` **CASCADE**; `shift_id` → `shifts` **CASCADE** |

Three consequences worth stating now:

1. **`attendance` has no unique constraint at all.** Duplicate check-ins are
   prevented only by application logic (§F), so any gap in that logic writes a
   real duplicate row. Contrast Wave 12.5's holidays, where the database was the
   backstop.
2. **`employee_schedules` enforces one row per employee per day**, so
   `generate_employee_schedule` must be idempotent or handle the collision — a
   detail to confirm per endpoint during implementation.
3. **Deleting a shift cascades into `employee_shift_assignments`.** Wave 12.5's
   `shifts/delete.php` is a *soft* delete, so this cascade is not reachable
   through that endpoint — but it is reachable through
   `company_delete_helper.php`, and it means a hard shift delete silently
   unassigns employees.

## E. D-083 audit — the largest exposure in Phase 1 so far

**11 of 18 endpoints** contain timezone-sensitive constructs:

| Endpoint | Constructs |
|---|---|
| `check_in` | `NOW()`, `TIMESTAMPDIFF`, `date()` |
| `check_in_qr` | `NOW()`, `date()` |
| `check_out` | `NOW()`, `date()`, `strtotime` |
| `create` | `TIMESTAMPDIFF`, `date()`, `strtotime` |
| `delete_range` | `DATE()`, `date()`, `strtotime` |
| `employee_monthly_attendance` | `TIMESTAMPDIFF`, `date()`, `strtotime` |
| `list` | `DATE()`, `TIMESTAMPDIFF`, `date()`, `new DateTime`, `strtotime` |
| `overall_report` | `date()` |
| `stats` | `DATE()`, `TIMESTAMPDIFF`, `date()`, `strtotime` |
| `update` | `date()`, `strtotime` |
| `employee_monthly_schedule` | `date()` |

This is qualitatively worse than earlier waves, for one reason:

**`check_in.php:56` writes the attendance timestamp with `NOW()`** — the
database decides when the employee checked in — while **`check_in.php:63`
reports `date('Y-m-d H:i:s')`**, the application clock. A single response
therefore mixes two clocks: the row's `check_in` comes from the database session
timezone, and the `time` field the client is shown comes from `LegacyClock`.
Until D-083 is closed those two disagree by the offset difference, in a value a
client displays to the employee.

The 2-hour duplicate guard (`check_in.php:35`) is also evaluated with `NOW()`,
so the window itself moves with the session timezone.

**D-083 is not closed by this wave and no `SET time_zone` is proposed.** It is
recorded here as materially more urgent than it was: earlier waves exposed
timezone-sensitive *reads*; this wave has timezone-sensitive **writes** whose
values become permanent rows.

## F. Check-in / check-out / QR map

### F.1 `check_in.php` — statement order

```text
method guard -> requireAuth() (any role) -> requireCompanyActive
-> body(); required(latitude, longitude, method)
-> employee_id = body.employee_id ?? auth.employee_id ?? 0   <-- see I.1
-> employee lookup scoped by id + company_id  (404 invalid_employee)
-> is_self_attendance = auth.type === 'employee' && auth.employee_id === employee_id
-> if (is_self_attendance && empty(is_mobile_attendance_enabled)) 403
-> attendance_find_open_session(employee_id)  -> already_checked_in
-> last check-in; TIMESTAMPDIFF(MINUTE, last, NOW()) < 120 -> 422
-> if (!empty(lat) && !empty(lng)) validate_employee_attendance_location(...)
-> INSERT ... VALUES (?, NOW(), ?, ?, ?)
-> ok(check_in_recorded, {attendance_id, time: date('Y-m-d H:i:s')})
```

No transaction anywhere. The open-session probe, the 2-hour probe and the INSERT
are three independent statements, so two concurrent requests can both pass the
probes and both insert — and there is no unique constraint to stop them (§D.1).

### F.2 Behaviours that must be ported literally

- **`required()` passes `"0"`, `!empty()` does not.** `latitude` and `longitude`
  are `required`, then geofence validation is guarded by
  `!empty($lat) && !empty($lng)`. A check-in at latitude `0` or longitude `0`
  therefore passes `required()` and **skips location validation entirely**. See
  §I.2.
- **The 422 carries a hard-coded Arabic string**, not a lang key:
  `'لا يمكن تسجيل بصمتين متتاليتين خلال اقل من ساعتين'` (`check_in.php:38`). It
  is returned as `Response::REASON` and is not translated for an English client.
- `method` is in `required()`, so the `?? AttendanceMethodEnum::APP` fallback on
  the INSERT is **dead code**. Reproduce the fallback anyway or drop it — it
  cannot change behaviour either way, and this document flags it so a reviewer
  does not read its absence as a defect.

### F.3 `check_in_qr.php`

QR is validated against **`branches.qr_code` plus an expiry**, scoped by
`company_id` (`check_in_qr.php:23-38`); a miss is `invalid_qr`. The matched
branch id becomes the attendance branch context. The insert records
`method = 'qr'`. No token, nonce or signature is involved — the QR value is a
stored column, so it is a **bearer secret with no replay protection** beyond its
expiry. Recorded as an observation, not a proposed change.

### F.4 Overnight and rollover

`check_out.php` uses `NOW()` and `strtotime`; whether a check-out after midnight
attaches to the previous day's open session is decided by
`attendance_find_open_session()`, which is in the helper closure and must be read
statement-for-statement during implementation. **Not yet fully traced** — flagged
as an implementation-time obligation rather than asserted here.

## I. Dirty-data, tenancy and security findings

### I.1 Any authenticated employee can record attendance for a colleague

`check_in.php:18` takes the target from `body.employee_id ?? auth.employee_id`,
and the only role check is a bare `requireAuth()`. The employee is then looked up
by id **and company**, so this is not cross-tenant — but within a company:

- an EMPLOYEE supplying another employee's id passes the lookup;
- `is_self_attendance` is then **false**, so the
  `is_mobile_attendance_enabled` check at `:26` is **skipped**;
- and `validate_employee_attendance_location` is called with
  `$is_self_attendance = false`, which relaxes the geofence for that call.

So an ordinary employee can check a colleague in, bypassing the colleague's own
mobile-attendance flag and a stricter location rule. Same shape on
`check_in_qr.php` and `check_out.php`. This is a real authority finding and it
needs a decision (§J.3), not a silent fix.

### I.2 Latitude or longitude of exactly zero disables geofencing

`required()` accepts `"0"`; `!empty("0")` is false. A caller sending
`latitude: 0` (or `"0"`, or `0.0`) satisfies the required check and then skips
`validate_employee_attendance_location` entirely. Null Island is a real
coordinate, so this is reachable by an honest client and trivially by a hostile
one.

### I.3 `attendance` has no unique constraint

Two concurrent check-ins can both pass the open-session and 2-hour probes and
both insert, because there is no transaction and no constraint (§D.1, §F.1).
Legacy has the same race; recorded so the port does not accidentally close it
with a constraint the schema does not have.

### I.4 Spreadsheet surface shares nothing with Wave 12.4

`attendance/analyze_excel.php` and `import_excel.php` require
`attendance_excel_analyzer.php`, which reaches `xlsx_parser.php` and
`schedule_helper.php`. **It does not use the employee spreadsheet helper at
all.** Wave 12.4's `LegacyEmployeeSpreadsheet*` stack, its 28-column metadata and
its D-085 reader corrections are therefore **not** transferable here on the
strength of the matching filenames. Only the format-level primitives
(`LegacyXlsxReader`/`Writer`, `LegacyCsvReader`/`Writer`) are candidates for
reuse, and each must be justified against `xlsx_parser.php` rather than assumed.

### I.5 Notification side effects

Only two endpoints in the wave have any: `attendance/import_excel.php` and
`schedules/assign_employee_schedule.php`. Both land on the D-082 call boundary
and hr-platform#22 still owns delivery.

## J. Owner decisions required before implementation

### J.1 `schedule_helper`'s `company_settings` dependency (blocking)

All three `schedules/*` endpoints, plus `attendance_calendar_helper` and
`attendance_excel_analyzer`, need
`company_setting_selected_values(company_id, WEEKLY_OFF_DAYS)`. That table is
item 13 and frozen.

Options, none of which I have taken:

- **(a)** Port a minimal read-only slice of `company_setting_values` /
  `setting_definitions` sufficient for `WEEKLY_OFF_DAYS`, recorded as an
  explicit, bounded exception to D-4.
- **(b)** Move item 13's settings read forward in full.
- **(c)** Defer every endpoint that reaches `schedule_helper` to a later wave —
  which removes all three `schedules/*` endpoints and, through
  `attendance_calendar_helper`, a large part of `attendance/list.php`.
- **(d)** Something else.

I recommend **(a)** as the narrowest, but the boundary is D-4's and the choice is
the owner's. Nothing is implemented either way until this is answered.

### J.2 `payroll_calculation.php` in the closure (blocking)

`schedule_helper` and `overall_attendance_report_helper` both call into
`payroll_calculation.php`, assigned to Waves 12.8/12.9. The same four options
apply: a bounded read-only subset, moving payroll forward, deferring the
consumers, or another shape. The exact functions called must be enumerated
before the decision is useful; that enumeration is small and I can produce it on
request.

### J.3 Attendance-on-behalf-of (security)

Reproduce §I.1 literally, or narrow it as D-076 narrowed HR privilege
administration? Reproducing preserves a real in-company privilege gap;
narrowing is a divergence with its own decision number. My recommendation is to
narrow — an ordinary employee recording a colleague's attendance has no
legitimate use I can see in the source — but this is squarely an owner call.

### J.4 Zero-coordinate geofence bypass (security)

Reproduce §I.2, or treat it as a defect? Reproducing is the ADR-0011 default and
is what I would do absent instruction; the counter-argument is that it defeats
the geofence entirely for a trivially guessable input.

### J.5 The hard-coded Arabic 422 reason

`check_in.php:38` returns an untranslated Arabic string as `Response::REASON`.
Reproduce byte-for-byte, or route it through the catalog? Byte-for-byte is
literal parity; a catalog key would change the wire response for an English
client.

### J.6 Scope confirmation

Confirm Wave 12.6 is **18 endpoints across `attendance` and `schedules`**, with
`employee_shift_assignments` recorded as a table without endpoints, already
written by Wave 12.4's employee paths. The Item 12 specification's module list
needs the same correction D-054 applied to `department_branches`.
