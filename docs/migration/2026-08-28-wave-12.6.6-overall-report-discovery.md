## 1. The two endpoints share one builder

`overall_attendance_report_build()`
(`apis/helpers/overall_attendance_report_helper.php`, 379 lines) is the whole of
both endpoints' business logic. Its own docblock says so: *"Shared by
overall_report API and attendance export."*

```text
attendance/overall_report.php ─┐
                               ├─→ overall_attendance_report_build()
attendance/export.php ─────────┘        (via data_export_attendance_csv():321)
```

`overall_report.php` strips the internal `_period_from` / `_period_to` keys and
calls `ok()`. `export.php` passes the same rows to the workbook writer.

**Consequence for sequencing: this is one port with two response shapes, not two
ports.** Building `overall_report.php` first leaves `export.php` owing only its
workbook rendering and its `type=fingerprints|details|days` second sheet.

## 3. Behaviours the port must preserve literally

Read out of the builder, in the order it applies them.

### 3.1 The period is clamped to elapsed days

```php
$as_of = payroll_calculation_as_of_date($period_to);
$range_to = payroll_period_in_progress($period_to, $as_of) ? $as_of : $period_to;
```

While the selected period is still open, only elapsed days enter attendance,
absence and paid-rest maths — future days are **not** absence. `total_days_in_period`
is `diff($period_from, $range_to)->days + 1`, or `0` when `$range_to < $period_from`.

Every downstream helper receives `$range_to`, not `$period_to` — except
`payroll_expected_work_days_until()`, which receives **both** `$period_to` and
`$as_of`. Passing `$range_to` there would change the result.

### 3.2 Missing dates fall back to the current month

`from`/`to` empty → `month`/`year` filters, defaulting to `date('n')`/`date('Y')`,
then `from = Y-m-01` and `to = date('Y-m-t')`. An unparseable date, or
`from > to`, is `fail(LangKey::INVALID_DATE, 400)`.

### 3.3 The holiday credit is gated on attendance coverage

```php
if ($present < WEEKLY_REST_MIN_COVERED_WORKDAYS) {
    $holiday_credit = 0;
}
```

Java's equivalent constant is `LegacyWeeklyRestCredit.MIN_COVERED_WORKDAYS = 3`.
The gate is applied **after** the query, on `present_days`, not inside the helper.

### 3.4 The absence formula

```php
$paid_due       = min(max(0, $expected_work_days_due),
                      max(0, $present) + $paid_leave_days + (int) round($holiday_credit));
$workday_absent = max(0, $expected_work_days_due - $paid_due);
$absent         = $workday_absent + max(0, $void_weekly_rest);
```

Unearned weekly rest counts as unpaid absence. `$holiday_credit` is rounded at
each use rather than once — `(int) round(...)` appears separately in `$paid_due`,
in `$paid_rest_days`, in `$effective_present` and in `paid_rest_details`, while
the row's own `official_holiday_days` carries the **unrounded** value.

### 3.5 Role scoping happens in the WHERE clause

- `employee` → forced to `e.id = auth.employee_id`; the `employee_id`,
  `branch_id` and `department_id` filters are **not** applied.
- `manager` → `sql_manager_same_branch_scope()` appended.
- anyone else → the three filters apply if non-zero.

### 3.6 Ordering is numeric-then-lexical on employee code

```sql
ORDER BY CAST(NULLIF(e.employee_code, '') AS UNSIGNED) ASC,
         e.employee_code ASC, e.first_name ASC, e.last_name ASC
```

SQL-observable ordering is part of the contract (D-111).

### 3.7 The empty-period row is a distinct shape

When `total_days_in_period <= 0`, `employee_id <= 0`, or `range_to < period_from`,
the builder emits a **zeroed row with the same keys** and `continue`s — it does
not skip the employee. `paid_rest_details` still carries its three labelled
entries with `value => 0`.

### 3.8 Row keys

24 keys, four of them nested lists (`present_details`, `absent_details`,
`exception_details`, `paid_rest_details`). `_period_from` and `_period_to` are
internal: `overall_report.php` strips them, `export.php` reads them for the
filename range.

`branch_name` and `department_name` are `null` when empty-string, not `''`.

## 6. Open questions and findings from implementation

### 6.1 Closed during implementation

**The fingerprints sheet was traced and delivered.** It turned out to be a
second, independent sheet rather than a variation on the first, and its
divergences are the interesting part — three rules differ from the report's
query **in the same endpoint file**:

| | Report query | Fingerprints query |
|---|---|---|
| Ordering | `CAST(NULLIF(employee_code,'') AS UNSIGNED)` | `CASE WHEN employee_code REGEXP '^[0-9]+$' THEN CAST(...) ELSE NULL END` |
| Numeric search | name **or** code | code **only** |
| `is_active` | not filtered | `= 1` |

It also has its own date fallback — this month's first and last day, not the
report's month/year filters — and its own error code for an inverted range,
`invalid_input` where the report gives `invalid_date`. All five are pinned by
test.

**G6 evidence depth — answered in practice.** O-7's floor is one measured
differential assertion per live endpoint. 12.6.6b and 12.6.6c went past it: a
case per behavioural branch, because every branch here would produce a
*plausible-looking* wrong report rather than an obvious failure. If the owner
wants the floor instead, the surplus cases are the ones to drop.

### 6.2 Found while implementing 12.6.6a–c

**A follow-up worth its own decision: two dead columns.** The employee query's
`att` subquery aggregates `total_duration_minutes` and `total_expected_minutes`,
the second through a correlated per-row shift lookup. **The builder reads
neither** — its loop uses only `present_days` and `exception_days`, and the row's
duration comes from `attendance_period_work_minutes()` instead. They are
reproduced in the port anyway, because dropping them is an optimisation rather
than a fidelity fix and D-058 puts the burden of proof on the change. Removing
them is invisible to every client and would cut a correlated subquery per
attendance row; it wants a measurement and a numbered decision, not a silent
edit.

**Two orderings, deliberately kept apart.** This query orders on
`CAST(NULLIF(employee_code, '') AS UNSIGNED)`; the attendance listing orders on a
`REGEXP '^[0-9]+$'` guard. They sort mixed alphanumeric codes differently —
MySQL casts `"12abc"` to `12` where the REGEXP guard yields NULL. SQL-observable
ordering is contract (D-111), so the report keeps its own rather than reusing the
listing's constant.

**The employee branch is unreachable from `overall_report.php`.** Its role list
is `[COMPANY_ADMIN, HR, MANAGER]`, so an EMPLOYEE is refused. The builder's
employee branch is live only through `export.php`, which authenticates with a
bare `requireAuth()`. Both facts are pinned by test.

**Two behaviours no one would guess from the row shape**, both now pinned:
a single punch with no check-out is not zero worked — legacy pays
`expected - ATTENDANCE_INCOMPLETE_PUNCH_DEDUCTION_MINUTES`, a two-hour
deduction; and an official holiday that was worked contributes worked minutes
against **zero** expected, which is what surfaces in the overtime column.

**A defect caught by testing rather than inspection.** The first draft of the
exception-details query joined `attendance_exception_types`. The table is
`exception_types`; it would have thrown on the first request.

### 6.3 Found while implementing 12.6.6d

**The overall sheet's overtime column is the one cell that is not `HH:MM`.**
Every other duration goes through `data_export_format_overall_duration()`, which
never returns blank — but the overtime cell shows a bare `0` when there is no
surplus, because the row builder tests `$overtime_minutes > 0` before formatting.

**Two duration formatters that look interchangeable and are not.** The overall
one gives `00:00` at or below zero; the day-level one gives an em dash for an
incomplete day and an **empty string** for a complete one with no minutes. Three
outcomes against one, which is why the `incomplete` flag is threaded through the
fingerprints row builder rather than derived at format time.

**The config gate runs after the `type` branch.** Disabling the fingerprints
sheet refuses it with 403; it does not fall back to the overall sheet. Pinned,
because falling back would look like graceful degradation.

**`app_config_value()`'s static cache is not portable as a field.** PHP's process
ends with the request, so that cache is per-request; holding it for a Spring
bean's lifetime would mean an operator flipping either flag never takes effect
until a restart. `LegacyExportSheetAvailability` reads per call and says why.
